# tsumiki(保育園向け勤怠)と ryus-apps への統合検討

> 最終更新: 2026-11-20 / ユーザー提供情報 + リポジトリ調査

## 概要
| 項目 | 内容 |
|---|---|
| 種別 | 保育園向け勤怠システム(要件定義 + プロトタイプ) |
| 最初の利用先 | **喜名保育園**(現行は KinaKintai:2014年頃の Delphi デスクトップアプリ + Oracle XE) |
| ryus-apps との関係 | **現在は無関係**。保育園の勤怠は**変形労働時間制**のため分けている |
| ユーザーの意向 | **まとめられるなら ryus-apps に取り込みたい** |

## 現行 KinaKintai の問題(as-is-analysis.md より)
- 打刻を ALSOK の入退室データに依存(Excel マクロで取込)
- 出勤 30 分切上げ・退勤 15 分切捨て、残業の自動カット → 実労働時間が記録されない(**法令リスク**)
- 有給の付与日数が手入力、年5日取得義務を管理できない
- 申請・承認が紙
- **平文パスワード、SQL インジェクションなど重大なセキュリティ問題**

## tsumiki に必要で ryus-apps に無いもの(差分)

| 要件 | tsumiki | ryus-apps の現状 | 取り込み時の対応 |
|---|---|---|---|
| 労働時間制度 | 通常・**1か月単位変形・1年単位変形**を園(雇用区分)ごとに設定 | 通常のみ。変形・フレックスは「制度ごとに別の作業」として**意図的に外している**(`docs/labor-settings.md`) | 集計を「制度ごとに差し替えられる」形にする(通常/1か月変形/1年変形) |
| 1年単位変形の運用 | 年間カレンダー・パターン(指定休)割当、途中入社者、休日の振替申請、**時間外の3段階判定**(日・週・対象期間) | なし | 新規(最も大きい) |
| シフト作成 | 月単位のグリッド作成、前月複写、基本パターンから一括生成、下書き/公開、休み希望、予定労働時間・休日数の表示 | 日単位のシフト変更のみ | 月次シフト作成画面を新規。**他業種(飲食・小売・介護)にも有用** |
| 締め日 | 未確定(Q11) | **末日締め固定** | 喜名保育園が末日締めでなければ、締め日の対応が必要(影響大) |
| 複数法人・複数園 | 必要 | テナント + 組織で表現可能 | 既存の仕組みで対応可 |
| 保育園固有 | 配置基準チェック、常勤換算、処遇改善資料(Phase 3) | なし | 「保育園オプション」として後から追加 |
| 打刻 | スマホ打刻(将来 IC カード・共用端末) | スマホ打刻あり | 対応可 |

## 統合の判断材料

**統合するメリット**
- 打刻・申請承認・有給・月次締め・CSV・テナント分離・認証を**作り直さずに済む**(tsumiki の Phase 1 の大半)。
- 変形労働時間制と月次シフト作成は、保育園以外(病院・介護・飲食・小売)でも需要が大きく、**ryus-apps の商品力が上がる**。
- 保守するコードが1つになる。

**統合の難しさ**
- 1年単位の変形労働時間制は集計ルールが別物。ryus-apps の集計(勤務表・締め・給与 CSV・有給)の作りに手を入れる必要がある。
- 締め日が末日以外なら、さらに集計の作りを直す必要がある。
- 喜名保育園の稼働時期に間に合うか(ryus-apps 本体の公開前に、特定顧客向けの機能を先に作ることになる)。

## 提案(たたき台)
1. **統合する方向で進める**(ユーザー意向どおり)。tsumiki のプロトタイプは画面・業務の検証用として位置づける。
2. 先に ryus-apps 側で「**労働時間制度を差し替えられる集計**」の設計を行う(通常のみ実装済みの状態から、拡張点を作る)。
3. 実装順:①月次シフト作成(汎用)→ ②1か月単位変形 → ③1年単位変形(指定休・3段階判定)→ ④保育園オプション(配置基準・処遇改善)。
4. 喜名保育園は ryus-apps の1テナントとして稼働させる。
5. 喜名保育園への未回答の確認事項(Q4〜Q14。特に **Q11 締め日**、Q8 法定休日、Q9 有給の付与方式)を先に回収する。
